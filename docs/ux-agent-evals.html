How a run works

Five stages, ordered by what it costs to be wrong

The order is not arbitrary and it is not alphabetical. Structural checks read the declarations and do no I/O, so they finish in milliseconds and cost nothing; a version whose tool table lets a call through from a closed state should never reach the stage that spends money on inference. Each stage is cheaper and more certain than the one after it, and the run stops at the first stage that fails structurally — though a failing fixture does not stop the fixtures after it, because knowing that one red flag missed is far less useful than knowing which three did.

STAGE I Structural Reads the declarations only. Every field key has a label and a schema; the break is reachable from every live state; no tool is permitted from a closed one. 2 cases · 12 assertions · ~40 ms
STAGE II Fixtures One utterance per red flag through the real gate, and one argument case per tool. Asserts the outcome and the invocation count. 17 cases · ~50 s
STAGE III Scenarios Whole synthetic patients driven through the scripted engine — completion, lockout, reschedule, abandonment, and a red-flag path that ends the call. 6 cases · ~2 min
STAGE IV Rubric The two report fields that are about writing rather than arithmetic, judged against fixed transcripts on named criteria — never on a similarity score. 16 cases · ~55 s
STAGE V Benchmarks Six hops timed from acoustic end, on three pipeline configurations, against the last published version. These produce numbers, not verdicts — which is why they are last, and why almost none of them can block a publish. 18 measurements · ~90 s

Four stages of pass-or-fail, then one stage of numbers. The colour tells you which is which.

The run

What failed, in the order it matters

It answers three questions, in this order:

  • Can this version ship?
  • Which case says no, and why?
  • What moved since the last one that shipped?

There is no overall pass percentage anywhere on this screen. 39 of 41 is a comfortable number and a useless one: the two that failed are the entire story, and a green ninety-five per cent above them would be a headline arguing with its own article.

Goal: a failing suite tells you which block to open, not which log to read.

Starting a run

Four choices, and then it runs

This is the clinician portal's deployment composer, doing a different job with the same four fields. That is deliberate. Choosing what to run against which version is the same shape of decision as choosing what to send to which patient, and a product that invents a new form layout per verb is a product with no verbs.

Nothing here reads a patient record. Every case is a synthetic transcript authored alongside the block it tests, and the scenario stage drives them through the scripted engine rather than a live call. That is what makes it safe to run this on every commit, and it is also why the results are reproducible: the same version and the same config give the same verdict.

Five triggers. The platform's own tests — the PHI canary, ledger integrity, projection rebuild, resumption — are not on this list: they test the engine, not this protocol version, and they do not get re-run because someone edited a question.

Benchmarks

Six hops, measured against the version that shipped

Every bar carries a dashed line, and the dashed line is v3 — the version currently in front of patients. A benchmark without a baseline is a number, and a number on its own has never once told anyone whether to ship. What matters is the direction and the size of the move.

The timings start at acoustic end — the moment the patient stops speaking — because that is where a person starts waiting. Timing from transcript arrival makes the endpointing hangover disappear from the chart, and the hangover is over a third of the wait.

Evals A verdict, and it blocks Deterministic, reproducible, and binary. The red flag fired or it did not; the tool was reachable from a closed state or it was not. There is no threshold to argue about and no judgement to exercise, which is exactly why a failing eval is allowed to stop a publish without a human in the loop. 41 casessame input, same verdict
Benchmarks A number, and you decide +49 ms is over budget and it does not block. A latency regression is a bad day; an unprovable red flag is a version whose safety behaviour nobody can demonstrate. Treating them the same teaches people to override the gate, and a gate that gets overridden weekly is decoration. One exception runs the other way: the endpointing hangover is a clinical setting, and a run that “improved” it to 400 ms would be a regression, not a win — that is the clipped clause where the red flag lives. 18 measurementsadvisory · shown on the gate

The gate

Fix the two, and the button turns on

The publish gate is the same component on both screens, showing the same four rows. It lives here because this is where the evidence is, and it lives in the studio because that is where the button is. Neither copy is authoritative — both read the last run.

When the two failures are fixed and the suite is green, publishing freezes the version: prompt blocks, red-flag set, tool states, report schema, model configuration, and the run that let it out. The run id is stored on the version, so “which suite passed for the version this patient was interviewed on?” is a lookup rather than an archaeology project.

The loop: the studio writes the blocks and compiles the suite, this screen runs it and names the block to go and fix, and the clinician portal deploys the version that came out. One artefact travels the whole way, and it is the same version id on the interview a patient answers.
